# Mobile Meeting Live 故障排查经验

> 本文记录本项目从“手机能采音但没有字幕”到“中/越/英实时转录并翻译成中文”的实际排障过程。
>
> 目标是帮助后续维护者快速判断故障位于：麦克风采集、浏览器上行、Cloudflare WebSocket 代理、Gemini Live 协议、下行消息解析、VAD 切句，还是浏览器缓存。
>
> **安全说明：** 本文不记录真实 API Key、Cloudflare 账号、真实部署地址或其他凭证。命令中的域名和密钥均为占位符。

---

## 1. 当前稳定架构

```text
手机浏览器
  ↓ Web Audio API / AudioWorklet
16 kHz、16-bit、单声道 PCM
  ↓ WebSocket
Cloudflare Pages Function：/ws
  ├─ 使用服务端 GEMINI_API_KEY 申请 ephemeral token
  ├─ 浏览器 setup 消息在上游 CONNECTING 时排队
  └─ 转发到 Gemini constrained WebSocket
  ↓
Gemini Live Translate
  ├─ inputAudioTranscription：原文
  └─ outputAudioTranscription：中文译文
  ↓
前端显示、时间戳、localStorage、Markdown/TXT 导出
```

当前生产前端采用：

- 模型：`gemini-3.5-live-translate-preview`
- 目标语言：`zh-CN`
- 浏览器连接相对路径 `/ws`
- 输入：16 kHz、16-bit、单声道 PCM
- 服务端自动 VAD 保持开启
- 前端自适应 VAD 在停顿后发送 `audioStreamEnd`
- `audioStreamEnd` 后 2 秒仍无 `turnComplete` 时，前端强制落一条带时间戳的记录

## 2. 最有效的诊断指标

页面诊断栏至少保留以下指标：

```text
麦克风电平
音频↑包数/KB
服务端消息↓数量
VAD 状态/阈值（如启用）
```

不要只看“有没有字幕”。根据指标可以快速分层：

| 现象 | 最可能故障层 | 优先检查 |
|---|---|---|
| 麦克风电平不动、上行包数为 0 | 麦克风权限或 AudioWorklet | HTTPS、权限、AudioContext、worklet 加载 |
| 麦克风电平正常、上行包数增长、下行始终为 0 | WebSocket setup、代理上游、旧版前端缓存 | 是否收到 `setupComplete`、close code/reason、线上 `app.js` 版本 |
| 下行消息增长但无字幕 | 前端帧解码或 JSON/字段解析 | `string / ArrayBuffer / Blob`、`inputTranscription` 字段 |
| 有原文但无中文译文 | 翻译模型或 `translationConfig` / `outputAudioTranscription` | setup 配置、模型 ID、完整服务端消息 |
| 很久才出现一整段字幕 | VAD 没切句或没有发送 `audioStreamEnd` | 底噪阈值、静音时长、`turnComplete` |
| 持续“连接断开/自动续接中” | 上游被拒、连接关闭、旧 JS 缓存、重连循环 | close code/reason、setup 错误、缓存版本号 |
| Node 验证通过但手机失败 | 浏览器差异、缓存或手机网络路径 | 真机 Safari/Chrome、线上资源版本、手机调试日志 |

### 最关键的分界线

- `音频↑` 增长：只能证明浏览器调用了 `ws.send()`，不代表 Gemini 接收成功。
- `服务端消息↓ ≥ 1`：通常表示至少收到 `setupComplete`，上下行链路基本建立。
- `服务端消息↓ > 0` 但无字幕：重点查前端解析，不要再改麦克风采集。
- `服务端消息↓ = 0`：不要先调 VAD，先查连接/setup/缓存。

## 3. 已确认的关键协议经验

### 3.1 Ephemeral token 必须配 constrained 端点

浏览器侧使用 ephemeral token 时，应连接：

```text
...BidiGenerateContentConstrained
```

不要把 ephemeral token 用在非 constrained 的 `BidiGenerateContent` 端点。API Key 直连和 ephemeral token 是两条不同认证路径。

### 3.2 Setup 字段位置必须按实测结构

当前项目验证通过的结构：

```js
{
  setup: {
    model: 'models/gemini-3.5-live-translate-preview',
    generationConfig: {
      responseModalities: ['AUDIO'],
      translationConfig: {
        targetLanguageCode: 'zh-CN',
        echoTargetLanguage: true
      }
    },
    inputAudioTranscription: {},
    outputAudioTranscription: {},
    realtimeInputConfig: {
      automaticActivityDetection: {
        disabled: false,
        prefixPaddingMs: 250,
        silenceDurationMs: 650
      }
    }
  }
}
```

已踩过的坑：

- `responseModalities` 放在 setup 顶层会返回协议错误。
- `thinkingConfig` 在当前 Live setup 中不可用，发送会返回 1007。
- 文档、论坛和不同模型版本可能不一致；以当前模型真实 WebSocket 返回为准。
- 修改 setup 时必须先做最小 setup 测试，再发真实 PCM。

### 3.3 必须按实时节奏发送 PCM

一次性快速发送完整 PCM，可能无法获得稳定转录。验证脚本应按实时节奏发送：

```text
16,000 samples/s × 2 bytes = 32,000 bytes/s
40 ms 一块 = 1,280 bytes
```

即每 40 ms 发送约 1,280 字节 PCM。

### 3.4 句尾信号决定转录延迟

实测中只持续发音频、长时间不发送句尾信号，Gemini 可能不返回输入转录。当前前端在检测到静音停顿后发送：

```js
{ realtimeInput: { audioStreamEnd: true } }
```

这是“有音频上行但迟迟没有字幕”最关键的修复之一。

## 4. WebSocket 代理的关键经验

### 4.1 必须处理上游连接竞态

浏览器 WebSocket `open` 后会立即发送 setup，但 Cloudflare 到 Google 的上游 WebSocket 可能仍是 `CONNECTING`。

错误做法：直接丢弃 setup。

正确做法：

1. 上游未打开时，把浏览器消息放入 `pending` 队列。
2. 上游触发 `open` 后按顺序补发。
3. 保持消息顺序，setup 必须先于音频帧。

如果丢了 setup，常见表现是：

```text
麦克风正常
音频↑持续增长
服务端消息↓0
字幕为空
```

### 4.2 不要猜测 Blob 的正文类型

Cloudflare Workers、Node 和浏览器对 WebSocket 消息的表示可能不同：

- 文本帧：`string`
- 二进制帧：`ArrayBuffer`
- 某些环境：`Blob`

代理端不要根据正文内容“猜是不是 JSON”。推荐：

- `string` 原样转发。
- `ArrayBuffer` 原样转发。
- `Blob` 明确转换为 `ArrayBuffer` 后再转发。

异步转换期间还要重新检查下游 WebSocket 是否仍为 `OPEN`。

### 4.3 前端统一兼容三种帧

前端应：

```js
socket.binaryType = 'arraybuffer';
```

并统一兼容：

```text
string / ArrayBuffer / Blob
```

`服务端消息↓` 应在 JSON 解析前递增。这样可以区分：

- 根本没收到消息；
- 收到了，但解码或 JSON 解析失败。

### 4.4 消息监听器必须先注册，再发送 setup

曾出现过 setup 发送后才注册 `message` 监听器的代码。移动网络环境下，`setupComplete` 可能快速到达并被错过。

稳定顺序：

1. 创建 WebSocket。
2. 设置 `binaryType`。
3. 注册 `message`、`close`、`error`。
4. 等待 `open`。
5. 发送 setup。

## 5. VAD、切句和时间戳经验

### 5.1 固定阈值在真实会议室不可靠

固定振幅阈值（例如 400）在安静环境可能工作，但会议室底噪、空调、扩音、手机自动增益会导致：

- 长期误判为“讲话中”；
- 一直不触发静音；
- 几十秒内容合并为一条；
- 时间戳看起来“消失”，实际是始终没有落条。

当前采用底噪自适应：

```text
noiseFloor = 指数滑动平均
threshold = max(250, noiseFloor × 2)
```

只在未处于讲话状态时更新底噪，避免把真实人声学进底噪。

### 5.2 静音时长是延迟与误切的平衡

- 太长：字幕和译文明显慢。
- 太短：一句话被切成多个碎片。

当前使用：

```text
最短有效语音：200 ms
句尾静音：500 ms
```

真实会议应继续观察：

- 中文自然停顿；
- 越南语连续短句；
- 会议室噪声；
- 远距离讲话。

不要仅凭合成音频决定最终参数。

### 5.3 `turnComplete` 不能作为唯一落条条件

翻译模型不一定及时发送 `turnComplete`。如果只在 `turnComplete` 时保存记录，可能出现：

- 多句话合并为一条；
- 时间戳只有一个；
- 用户误以为没有时间戳。

当前兜底策略：

1. VAD 判定句尾并发送 `audioStreamEnd`。
2. 等待模型返回转录与译文。
3. 2 秒内没有 `turnComplete`，前端强制把当前内容落成一条记录。

## 6. 失败实验：不要直接在手机生产路径复用

### 手动 `activityStart` / `activityEnd` + 关闭服务端自动 VAD

该方案在 Node 脚本中曾验证通过，但部署到手机后出现：

```text
音频↑增长
服务端消息↓0
页面反复“连接断开/自动续接中”
```

最终回滚为：

```text
服务端自动 VAD 开启
前端自适应 VAD 发送 audioStreamEnd
```

经验：

- Node WebSocket 通过，不代表 iOS Safari/Chrome 生产路径通过。
- 不要同时改“连接协议、代理转发、VAD、前端解析”四层。
- 每次只改一层，并保留上一个已被真机确认的基线 commit。
- 失败实验可以保留在独立测试脚本中，但不要把它当作生产验证脚本的唯一行为。

## 7. 浏览器缓存：最隐蔽的真机故障来源

曾出现代码已回滚并重新部署，但手机仍反复断开。原因是旧标签页或 iOS Safari 继续使用旧版 `app.js`。

最终做法：

```html
<script type="module" src="/app.js?v=<content-hash>"></script>
```

每次修改前端后更新内容哈希，让资源 URL 变化。

真机排查步骤：

1. 检查线上 `index.html` 引用的 `app.js?v=...`。
2. 检查线上 `app.js` 是否包含当前版本特征代码。
3. 完全关闭手机浏览器及旧标签页。
4. 重新打开页面测试。
5. 仍失败时，再检查 Safari Web Inspector，而不是继续盲改服务端。

经验：

> “已经部署”只说明文件上传成功，不代表手机正在执行新文件。

## 8. 推荐的端到端验证顺序

### 第 1 层：静态检查

```bash
node --check public/app.js
node --check functions/ws.js
```

### 第 2 层：最小 setup 测试

只连接 WebSocket 并发送 setup，必须收到：

```json
{"setupComplete": {}}
```

如果收不到，不要开始调音频和 VAD。

### 第 3 层：真实 PCM 测试

使用 16 kHz、16-bit、单声道 PCM，按 40 ms / 1,280 bytes 实时分块发送。

期望至少收到：

```text
setupComplete
inputTranscription
outputTranscription
```

运行示例：

```bash
MEETING_WS_URL="wss://<your-project>.pages.dev/ws" \
node scripts/verify-ws.mjs /path/to/16k-mono.pcm
```

### 第 4 层：浏览器环境测试

在桌面浏览器真实 WebSocket 环境验证帧类型和 `setupComplete`，不要只用 Node。

### 第 5 层：手机真机测试

检查：

- Safari 和 Chrome；
- 麦克风电平；
- 上行包数；
- 下行消息数；
- 原文；
- 中文译文；
- 每句时间戳；
- 断线续接；
- 旧标签页/缓存。

只有真机通过，才能宣称移动端故障已解决。

## 9. 症状驱动排障流程

### A. 音频↑0

1. 页面是否 HTTPS。
2. 麦克风权限是否允许。
3. `getUserMedia()` 是否报错。
4. AudioWorklet 是否成功加载。
5. AudioContext 是否因手机手势限制处于 suspended。

### B. 音频↑增长，服务端消息↓0

1. 是否收到 WebSocket `open`。
2. setup 是否被发送。
3. 浏览器 `message` 监听是否在 setup 前注册。
4. Cloudflare 上游未 open 时是否正确排队。
5. token 是否创建成功、额度是否正常。
6. setup 字段是否被模型接受。
7. 手机是否仍加载旧版 `app.js`。
8. 记录 WebSocket close code 和 reason。

### C. 服务端消息↓增长，但无字幕

1. 消息是 `string`、`ArrayBuffer` 还是 `Blob`。
2. `TextDecoder` 是否正确使用。
3. `JSON.parse` 是否失败。
4. 是否存在 `serverContent.inputTranscription.text`。
5. 诊断计数是否在解析前递增。

### D. 有原文，无译文

1. 模型是否是 Live Translate 模型。
2. 是否配置 `translationConfig.targetLanguageCode = 'zh-CN'`。
3. 是否启用 `outputAudioTranscription`。
4. 查看完整 `serverContent`，不要只查 `inputTranscription`。
5. 使用英文或越南语真实音频测试；用中文输入测“翻译成中文”可能看起来像没有翻译。

### E. 字幕或译文慢

1. 是否一直没有触发句尾。
2. VAD 是否被底噪卡在“讲话中”。
3. 静音时长是否过长。
4. `audioStreamEnd` 是否发出。
5. 翻译模型本身按语义单元输出，译文通常晚于原文。
6. 不要用一次性快速发送 PCM 的测试结果推断实时延迟。

### F. 一直断开和续接

1. 显示并记录 close code/reason。
2. 检查 setup 是否返回协议错误。
3. 检查 Gemini 项目额度或 spending cap。
4. 检查 token 获取是否限流或失败。
5. 检查代理是否在上游瞬时 error 时立即关闭客户端。
6. 检查手机缓存是否仍执行失败实验版本。
7. 重连必须带退避；不要 1 秒无限重试掩盖原始错误。

## 10. 已遇到的具体错误及含义

| 错误/现象 | 含义 | 处理 |
|---|---|---|
| `1007 Unknown name ...` | setup 字段位置或字段名不被当前模型接受 | 最小化 setup，逐字段加入并实测 |
| `1011 monthly spending cap` | Gemini 项目消费额度达到上限 | 调整额度后重新测试，不要继续改前端 |
| `setupComplete` 有、无转录 | 音频或句尾信号问题 | 实时分块发送 PCM，并发送 `audioStreamEnd` |
| `"[object Blob]"` | 代理错误地把 Blob 字符串化 | 按帧类型转发或转 ArrayBuffer |
| 下行消息很多但字幕空 | 前端没有正确解码二进制/Blob | 设置 `binaryType` 并统一 decode |
| 手机始终跑旧行为 | 浏览器缓存旧 `app.js` | 内容哈希版本号 + 关闭旧标签页 |

## 11. 安全红线

1. `.env` 必须加入 `.gitignore`。
2. 真实 `GEMINI_API_KEY` 只放：
   - 本地 `.env`；
   - Cloudflare 加密 Secret。
3. 不得把 API Key 写入：
   - 前端 JavaScript；
   - README；
   - 排障文档；
   - 测试脚本；
   - Git commit；
   - 日志输出。
4. 公开文档不得记录真实 Cloudflare 部署地址、账号、token 或 account ID。
5. 示例统一使用：

```text
https://<your-project>.pages.dev
GEMINI_API_KEY=<your-key>
```

## 12. 后续优化建议

按优先级排序：

1. **增强可观测性**
   - 页面显示最后 close code/reason。
   - 显示 `setupComplete`、原文、译文、解析错误计数。
   - Cloudflare 代理输出结构化日志，但禁止记录 token 和音频正文。
2. **修复重连策略**
   - 指数退避而不是固定 1.2 秒循环。
   - 达到阈值后停止重试并把真实原因显示给用户。
3. **统一验证脚本和生产协议**
   - 当前验证脚本可独立覆盖协议实验，但生产验证应增加与前端完全一致的 auto-VAD + `audioStreamEnd` 模式。
4. **长会话连续性**
   - 研究 Gemini session resumption，减少周期重连的音频缺口。
5. **翻译质量**
   - 可配置术语表和项目上下文。
   - 分开统计原文稳定时间和译文稳定时间。
6. **自动更新缓存版本**
   - 构建/部署时自动为 `app.js` 生成内容哈希，避免人工遗漏。

## 13. 维护原则

- 先复现，再修改。
- 先确定故障层，再改代码。
- 每次只改一个层次。
- 保留真机验证过的基线 commit。
- Node 通过 ≠ 浏览器通过 ≠ 手机通过。
- 文件已部署 ≠ 手机已加载新文件。
- 没有真实端到端结果时，不宣称“已完全解决”。
